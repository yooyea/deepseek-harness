# Agent Note: 租户控制平面重建可丢弃的 Harness 实例

Status: implemented

[English](2026-08-14-tenant-control-plane.md) | 中文

## Problem

Harness 当前没有经过认证的账户、租户归属或角色模型。在一个共享实例前配置多个代理凭据，仍然无法隔离会话、工作区、设置、插件和故障。

容器内安装插件也会让生命周期恢复失去明确依据。被修改的 profile 可能导致 Harness 无法启动，而只写入容器的插件产物会在容器替换后消失。

## Decision

DeepHarness 租户管理运行在 Harness 包图之外。一个租户对应一个受资源限制且可丢弃的 Harness 容器和一个主机端口。PostgreSQL 保存租户身份、可重建的加密凭据、资源策略、操作历史，以及插件期望版本、实际版本和最后健康版本。

私有阿里云 OSS 保存不可变插件包 tarball 和压缩的 PostgreSQL 逻辑备份。每个对象路径包含租户、插件和版本。提交上传记录时必须使用属于当前租户的路径，并通过 SHA-256 校验。租户容器只获得短期对象地址，不会获得阿里云凭据。

租户 `/data` 使用 tmpfs。Harness 启动前，镜像使用经过哈希查询且加密保存的租户运行令牌请求控制平面，下载期望插件版本，校验每个摘要，并在禁用包生命周期脚本的情况下安装精确 tarball。失败版本不会进入启动配置，并会在协调时被记录；基础进程仍可用于恢复。

租户镜像提供 `deepharness-plugin-publish` 并注入工作区操作说明。生成的可安装 bundle 会先打包，通过短期 URL 上传并登记为不可变期望状态，成功后才允许请求自身容器重建。上游进程内 `cordis_define` 定义不会被误报为持久化插件；它们必须先整理为可安装 bundle。

控制平面重建租户时会移除带管理标签的容器、轮换运行令牌、解密 Basic Auth 密码，并根据 PostgreSQL 状态创建替代容器。安全恢复会设置 `DSH_PLUGIN_SAFE_MODE=1`，不恢复租户插件。运行时只有在 Harness HTTP 就绪后才上报实际插件，因此启动阶段失败的进程无法把版本提升为最后健康版本。

PostgreSQL 只在 Compose 内部网络开放，并使用一个持久化数据库数据卷。独立控制平面进程每天把逻辑表状态导出为加密 OSS 对象。租户容器和插件产物不依赖 Docker 数据卷。

## Alternatives considered

- **在 Harness 核心增加租户归属**：未采用，因为会话、工作区、设置、凭据、API、WebSocket 和每个插件都需要面向当前用户的鉴权。
- **保留 SQLite 和租户 Docker 数据卷**：未采用，因为单台主机仍然是实例和插件恢复的权威来源，无法在另一台机器可靠重建。
- **把 OSS 挂载为插件文件系统**：未采用，因为对象存储不提供 Node 包解析和插件安装需要的文件系统语义。
- **向每个租户提供 OSS 凭据**：未采用，因为被攻破的插件可能访问其他租户产物或备份；短期对象地址可以保持租户隔离。
- **执行包生命周期脚本**：未采用，因为安装脚本运行在 Cordis 生命周期之外，并可能在插件校验前修改容器。

## Consequences

- 租户容器可以在不保留可写层的情况下，根据 PostgreSQL 和 OSS 删除并重建。
- 插件状态区分管理员意图与运行时观察，应用可访问之前不会把版本标记为健康。
- DSH 会话和工作区数据仍然是租户容器内的临时数据，直到相应存储 Provider 获得数据库和对象存储实现。
- PostgreSQL 成为额外运维依赖，其数据卷仍不可省略；OSS 逻辑备份用于主机丢失后的恢复。
- Docker Socket 仍然拥有主机级权限，必须部署为受认证保护的管理组件。
